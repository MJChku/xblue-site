CcNoc: a cache-coherent multicore memory system in XBlue

This is the XBlue tutorial example. It takes a real Bluespec design, a two-core RISC-V system with private MSI-coherent L1 caches, a distributed shared L2 with a directory, a network-on-chip and main memory (MJChku/bsv-cc-noc-design), and works through five steps:

  1. Port it to xblue modules, rule for rule, keeping its behaviour cycle for cycle.
  2. Measure the port against bsc's own Verilog: equal outputs and state in every cycle (co-simulation), then Yosys area/depth and simulation speed.
  3. Redesign the L1 data cache as non-blocking (MSHRs, hit-under-miss, miss-under-miss, merged secondary misses), keeping its interfaces.
  4. Measure again: an invariant monitor on random multicore traffic, the repo's programs, cycles, and area.
  5. Hand-optimize the SystemVerilog the lowering produces (router, core), keep it equal to the lowered module cycle for cycle, and state the proofs of that.

Numbers in this file come from the scripts in tests/ on this machine (48 cores, shared); tests/ says how to rerun each one.

          core0 ── L1I/L1D ─┐                   ┌─ L1D/L1I ── core1
                          node0 ── router0 ══ router1 ── node1
               L2 slice + directory ┘   │   └ L2 slice + directory
                                    main memory

Step 1: the port

Rules, one for one

Every rule of the original is a rule of the port with the same name, guard and actions (processInMsgReqReceiveL2, handleWaitFill, rl_Switch_Arbitration, …), and every module is an xblue module with the original's state under the names bsc gives it in Verilog (node0_cacheD_mshr, router0_inputBuffer_0_ff_head, core0_rv_core_pc). What has to be translated is Bluespec's scheduling, because XBlue has none: the designer writes the order of the rules of a cycle.

The order is bsc's own. bsc -show-schedule writes the logical execution order of each synthesized module (mktop_pipelined.sched); Top.lean's schedule is that order, with each separately synthesized module's rules (router, L2, core) placed where bsc puts them between its methods (for the router: after the putFlits, before the getFlits, since everything there is a bypass).

Two kinds of state. In Bluespec a register read sees the value at the start of the cycle; a CReg/EHR port sees the earlier ports' writes. In an XBlue ≫ chain every register behaves like the EHR: a later rule sees an earlier rule's write. So:

  • CRegs, EHRs, mkBypassFIFO, mkPipelineFIFO and the design's Ehr are plain XBlue registers: bsc's order puts their ports in order already.
  • bsc's Verilog primitives (FIFO1.v, FIFO2.v, SizedFIFO.v, BRAM1Load.v, BRAM1BE.v) read their registers at the start of the cycle. Each is an XBlue module, register for register, whose methods only drive wires (enqW, enqD, deqW); one rule, commit, updates it, and every commit runs after everything that uses the primitive. (Prims.lean; each is checked against bsc's Verilog on its own: tests/LibWrap.bsv.)
  • bsc may order a rule that writes a plain register before a rule that reads it, when the two can never fire in the same cycle (their guards exclude each other at the start of the cycle). Under ≫ the second rule would see the write and fire too. This is the one real trap of the port. Two cures, both used: move the writer later (the router's doInitialize), or test a start-of-cycle copy (mshr0, reqSent0, ppReqState0, trackIMem0: a snapshot rule at the start of the cycle copies the state register into a wire). Lint.lean's hazards lists every (reader, register, earlier writer) in a schedule, to review.
  • Vectors of registers that bsc reads by a dynamic index (cache metadata, directory, register file, BTB) are XBlue arrays (RegFile), which read the start of the cycle exactly like a register. Where an EHR port of such a vector is read after the write (register file, BTB), the one write of the cycle is forwarded with wires.

Guards. A Bluespec rule's guard includes the implicit conditions of the methods it calls; with --aggressive-conditions (the repo's flag) a condition inside an if is lifted as cond → ready. The port writes every guard out. bsc does not lift a condition that depends on the result of an ActionValue method of a separately synthesized module (a router's getFlit, the core's getDReq): there the guard is the unconditional ready (rl_enqOutLatch waits for a free latch even with no flit; requestD needs the L1's BRAM credit even for a store). The .sched file prints each predicate; the port follows it. Two conflicting rules where one is more urgent (afterCAUInMsgReq vs waitCAUResp, sendL2ToMem vs handleICacheOut) get a wire set by the more urgent one.

Don't-cares. A ? in BSV is AAAA… in bsc's Verilog, except where bsc reuses a nearby value (an L2 read request carries the old request's data; a union's padding is the network flit's bits). The port uses the same values (dc…, Prims.lean), so the state of the two designs is equal bit for bit.

What is not ported: the Konata pipeline log ($fopen/$fdisplay, its file handle register); the original top's second BRAM (bram, 2^30 words, never accessed); $displays. Main memory's RAM (2^26 lines of 512 bits = 4 GiB) is outside the XBlue design (mkBRAM1ServerExt): an XBlue array's semantics is one bit vector, and Lean cannot build one of 2^35 bits. The design keeps the BRAM's request register and the server adapter; the testbench holds the RAM and answers with BRAM1Load's timing.

Lint.lean's hazards on the finished mkTop lists four (reader, register, earlier writer) triples, all of one kind: core<i>_requestI/D read the L1's cau_upto_date after its handleWaitFill may have written it; the two need an empty and a non-empty in-queue, so they never fire together.

Problems met in the XBlue front end (worked around, not fixed)

  • A vector-element write v[i] <= x inside an else branch mis-sizes the element (L1NB.lean gives each write its own if).
  • line[…] on a let-bound local named line fails to parse; meta and initialize are Lean keywords; doc comments (/-- -/) cannot precede xblue commands.
  • A register may be written once per rule even under exclusive ifs; such writes are merged into one conditional expression.

Step 3: a non-blocking L1 data cache

The original L1 blocks: a miss (mshr = WaitFillResp, cau_upto_date = 0) stops every later request, loads and stores alike, until the line arrives through the NoC, the directory and maybe main memory. L1NB.lean's mkCacheNB#(nMSHR) replaces it, with the same ports: the processor side (putFromProc, getToProc, load answers in program order, stores unanswered) and the two message FIFOs, with the same messages. The node, the NoC, the directory and the core are unchanged (NodeNB.lean is Node.lean with the other cache; TopNB.lean the same top).

 putFromProc ─► lq (4 loads, oldest first) ─► loadPerform ─┐ hit: read the word
             └► sq (4 stores, in order)  ─► storeHead ─────┤ miss: an MSHR
                                                            ▼
                     MSHRs (nMSHR, one per set) ─► Req (S or M) + victim Resp ─► directory
 directory ─► fill (Resp): install, free the MSHR;  downgrade (Req): answer, I/S
 getToProc ◄─ lq head, once performed
  • MSHRs (nMSHR, a parameter: mkTopNB1/2/4). A miss allocates one: it evicts the set's line (a writeback Resp with data if it was M, a notice if S, as the original) and sends the upgrade Req (S for a load, M for a store); an S→M upgrade keeps its line meanwhile. At most one MSHR per set: the directory keeps one line per L1 set, so two lines of a set may not be in flight.
  • Hit-under-miss, miss-under-miss. Each cycle the oldest load that can go (ready: not blocked by an older store to its word, no MSHR on its line) performs: it reads its word if the line is present, else allocates its own MSHR. So a hit is served while misses are outstanding, and a second miss starts while the first is.
  • Secondary misses (an access to a line that has an MSHR) do not send a request: they wait on that MSHR and are satisfied by its fill.
  • Stores perform in program order, at the head of sq, once the line is M: write-back, the data goes to memory when the line is evicted or downgraded.
  • Memory order. Answers leave lq in program order. A load may perform before an older one (hit under miss); it keeps its value only while its line stays in the cache: when the line goes (downgrade to I, eviction) every performed-but-unanswered load of it performs again (replay). So loads stay ordered and stores ordered; a load may pass an older store to another word (TSO). The repo's programs synchronise by message passing, which TSO keeps.
  • Races with the protocol. A downgrade request is answered at once from the line's state: with data if M, I if the line is not there, which is also the answer while its own miss is outstanding (the directory then serves our request after). A fill and a downgrade never arrive in the same cycle (one message per cycle leaves the in-queue). A victim's writeback and the upgrade request leave together, the Resp first (the out-queue serves responses first, and the directory too), so the directory has the victim back before it serves the new line.

The arrays (tagsA, lines) read the start of the cycle, like the original's registers; the rules of a cycle see each other's writes through metaNow / lineNow (the fill or downgrade, the store, the eviction), in the order fill / downgrade ≫ storeHead ≫ loadPerform ≫ getToProc ≫ putFromProc. Here the sequential ≫ is the tool, not a trap: a fill frees its MSHR for the load rule of the same cycle, a store's dequeue unblocks the loads behind it.

Step 4: is it correct? is it faster? what does it cost?

The invariant monitor

tests/sys_nb.py runs a whole system in Verilator (the emitted SV, the main-memory RAM) with a monitor in C++ on the L1s' dbg* events, checked every cycle:

  • single writer / multiple readers: a shadow of each L1's line states (fills, downgrades, evictions); when a line's state changes, at most one L1 holds it in M, and then no other L1 holds it;
  • data value: a golden memory starts as the program image and takes every store at the cycle it performs in an L1 (the serialization point); every load that performs must read the golden value of its word at that cycle, from an L1 that holds the line, and the answer the core gets must be that load's last performed value;
  • no lost or duplicated requests: the monitor keeps each L1's loads and stores in program order from the accept events; a store that performs must be the oldest one, a load that performs must be one that was accepted, an answer must go to the oldest load and only once it has performed, and no request may wait more than 20 000 cycles (a deadlock or a lost request).

Random traffic (tests/randprog.py): two-core RV32I programs, 400 random operations per core (word/half/byte loads and stores, ALU operations, short branches, MMIO prints) on 2 lines per L1 set × 4 sets, 8 KiB apart, so that both cores write the same words, lines evict each other in the L1 and alternate home nodes. rand<seed> shares the data between the cores, prand<seed> gives each core its own (evictions without sharing).

Two bugs of the original, found on the way

The random programs first used 4 tags per set. Both the original (bsc's own Verilog and Bluesim) and every port stop within a few hundred cycles on them:

  1. The L2's writeback deadlocks the node. Node.bsv lets one main-memory request out at a time (trackL2Mem) and waits for its answer (getMemResp); main memory answers reads only (responseOnWrite: False). The first dirty L2 eviction (a write) waits forever. The repo's programs never evict a dirty L2 line; 2 tags per set keep the random programs clear of it too.
  2. A downgrade racing an eviction deadlocks the directory. In the blocking L1 the downgrade lookup and the processor's request share the CAU: the lookup can answer with the state the line had before the processor's miss evicted it. The directory then gets the eviction (to I) and after it an answer for a line it has as I everywhere; processInMsgResp never dequeues such a response, and the home node stops. (Bluesim's trace shows ERROR: … processInMsgResp forever.) The non-blocking L1 never answers a downgrade for a line it does not hold: the eviction already told the directory.

With 2 tags the original still stops on shared random programs (bug 2), and the stage-1 port with it, cycle for cycle (below); the non-blocking system runs them to the end.

The gain is small, and that is the core's doing, not the cache's: the 4-stage core stalls in writeback until its load answers, and it has at most two loads in flight (its dreq FIFO), so the cache rarely sees more than one miss at a time. Stores no longer stop the core (mc_hello_main32, which streams stores through a software FIFO, is 12% faster), and a hit under a store miss goes on. One MSHR already captures nearly all of it; more MSHRs change the cycle counts by a few cycles. A core that kept going past a load miss would get more out of the same cache.

The non-blocking cache keeps the same 64 Kbit of data and a few hundred bits of queues, so its flip-flops are the blocking one's (a little fewer: no CAU pipeline FIFOs). More MSHRs cost little (a 29-bit entry and a comparator each). A first version with a read port per use and two write ports was 417K cells; sharing ports brought it to the numbers above.

Step 5: hand-optimized SystemVerilog

The lowering gives a VB module (XBlue.Lower.lower d); what Yosys sees is that module printed. Here that module is optimized by hand, keeping the ports, the registers and the behaviour in every cycle, so that it can be proved equal to the lowered module and through it to the XBlue design. Opt/PLAN.md has the files, the statements and the proof plan; Opt/build.py router|core redoes everything below.

How. A hand-optimized module is written as Verilog (Opt/RouterOpt.sv; the core starts from the lowered core's SV, Opt/from_lowered.py), elaborated by VB and printed back by VB's emitter (lake exe vb emit) for Yosys and Verilator, so the numbers are those of the VB module the theorems are about. (The numbers below were measured with the earlier embedding's emitter; Opt/build.py remeasures.)

Same behaviour. Opt/opt_cosim.py runs the optimized module and the lowered one in one Verilator miter (3 seeds × 100 000 cycles, the module tests' stimulus, enables free of RDY in a quarter of the cycles) and compares every output bit before and after every edge, RDY or not, and every register of the optimized module with the lowered register, slice or array entry it stands for (the proof's state relation). Router (27 outputs, 117 registers), core (9, 257), L1 (10, 309), L2 (6, 533): equal in every cycle.

The router (51% fewer cells than the lowered one, 12% fewer than bsc's, one level shallower, the same flip-flops). Yosys's coarse netlist of the lowered router showed where the logic went:

  • The crossbar. Each 5160-bit row cbSwitch_i is written by the traversal (one slot) and cleared by five output rules (one valid bit each). Its next state is a rule-guard mux around a concatenation of per-slot muxes, then five bit clears: Yosys found no enable for the data bits (5 × $sdff of 5155 bits behind a 5160-bit mux) and kept two 1032-bit muxes per slot: 75 of the lowered router's 170 flit-wide muxes compute "keep the register". Here each slot is its own register (if (write) slot <= first), a plain enable.
  • Enables that a shared mux blocks. The crossbar output reads each slot as it is after this cycle's traversal (write ? first : slot), the same mux as the slot register's input. A first version that kept that mux shared got no enable on the 25 slot registers (Yosys makes a feedback mux an enable only when nothing else reads it). The output is computed as "the newest written flit if no valid older flit is above it, else the oldest valid one", which shares no mux with a register.
  • FIFO lanes. One register per lane of the input FIFO's 3-entry ring (a part-select write into one 3093-bit register prints as shift-and-mask), and the ring read is two muxes (the lowered read has three).
  • Wire defaults. enqD = en ? x : 0 gates every enqueued flit, twice per input FIFO: dropped where every reader is under en; the output's gate is folded into the selects of the old-flit mux (no 1031-bit AND).
  • Depth. The grant bits are written flat, and the traversal's guard no longer waits for the grants (only input 0 can hold a grant without asking: the arbiter's default winner).

The written-flit mux is a chain, not a balanced tree: with a tree ABC kept the depth one level lower (41) and spent 15,000 more cells on it (93,692).

The core (31% shallower than the lowered one, 29% shallower than bsc's, 3% more cells than the lowered one). The longest path ran from d2e through execute's redirect into fetch: the effective address adder (ripple carry, 60 levels in this flow) feeding the MMIO test of execute's guard; the misprediction test ppc != nextPc after the target mux; fetch's pc + 4 after the redirect mux. Changes: a sum compared with a value is tested without carries (a + b + c == k iff the carries t = a ^ b ^ k are the ones a and b produce: t[0] == c, t[i+1] == maj(a[i], b[i], t[i])); the misprediction is compared per candidate target; nextPc + 4 comes from the candidates (pc + 8, pc + (imm + 4), (rv1 + (imm + 4)) & ~1); each FIFO2's data register is a mux with an enable instead of an AND-OR (equal under FIFO2's invariant "never full and empty at once", which the state relation includes).

Where it does not win: L1 and L2. Their logic is dominated by the data arrays (the L2's 256 × 512-bit RAM is about 130,000 read-mux cells), the same in every version. The FIFO2 rewrite saves a few hundred gates (L1: 112,547 against 112,939 for the same module without it), but the import used then had no arrays: written out as registers and mux trees (from_lowered.py) they cost more than the lowered module's arrays after Yosys's memory_map (L1 with its arrays written out and nothing else changed: 140,355 cells / 112,939 gates / path 59, against 135,852 / 109,473 / 58). Optimizing them needs the lowered module's memories kept as they are (VB keeps them as memories), with the patches made on the lowered module itself. The non-blocking L1 was not attempted.

Proofs. Not done here: XBlue/PROOF-TODO.md (packages O1–O2) states them on VB (the optimized and the lowered module as Mealy machines, bisimilar under a state relation that is register equality plus, for the core, FIFO2's invariant). On the earlier embedding, the core's generated step proof closed (37 minutes, 13 GB) and the router's left 54 of 144 cones at the SAT timeout, presumably the flit-wide ones.

What is left

  • The router costs 1.8× bsc's logic as lowered (see the PPA notes); the hand-optimized module of step 5 costs 0.88× bsc's. A lowering that gave a register written by two rules one enable and one data mux, and split a row register written slot by slot, would get most of it automatically.
  • Step 5's equivalence proofs (Opt/PLAN.md).
  • The non-blocking L1 costs more than the blocking one (two read ports on its data array, forwarding, the queues); its depth is the deepest of the design. Pipelining the lookup would bring the depth down.
  • The two deadlocks of the original (the L2's memory writeback, the downgrade/eviction race in the directory's processInMsgResp) are in parts this example keeps unchanged; the non-blocking L1 avoids the second.
  • No Lean proofs here: the evidence is co-simulation against bsc and the monitor. The emitted SV comes from the verified lowering.
